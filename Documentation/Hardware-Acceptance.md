# Аппаратная приёмка: GoXLR → AudioPatch → Discord

Не ставьте отметку PASS на основании сборки или unit tests. Нужен реальный системный
HAL, микрофонный сигнал и прослушивание/запись в клиентах.

## До запуска

- GoXLR Utility настроен; AudioPatch не меняет настройки микшера GoXLR.
- Audio MIDI Setup: GoXLRMini 48 kHz. При live discovery 2026-10-26 подтверждены:
  21 input, 10 output, 24-bit Integer; input 3/4 — Chat Mic Mix L/R,
  input 7/8 — GoXLR-Mic L/R (processed), buffer 512 frames.
- Установлен именно AudioPatch.driver, Mac перезагружен, UI: «Драйвер загружен».
- Создан микрофон 2 ch/48 kHz, физический UID выбран, матрица 3→1, 4→2 сохранена.
- TCC разрешает микрофон AudioPatch. Для Discord и Chrome — собственные разрешения.

## Тест сигнала

1. Запустить маршрут, говорить в микрофон. В диагностике растут captured/rendered/written
   frames, peak реагирует на голос. Нулевой peak означает отсутствие сигнала в выбранном
   GoXLR mix; перепроверьте Utility и сравните с каналами 7–8, не изменяя исходный проект.
2. Audio MIDI Setup: input GoXLR Discord Mic содержит ровно 2 канала, 48 kHz.
3. QuickTime → новая аудиозапись → GoXLR Discord Mic. Записать 60 секунд речи и тишины.
   Прослушать: нет дребезга, периодических разрывов, ускорения/замедления или старого звука.
4. Discord Desktop → Voice & Video → Input Device → GoXLR Discord Mic.
   Провести mic test и реальный звонок не менее 10 минут. Сначала отключить auto gain,
   noise suppression и echo cancellation для диагностики; затем проверить с обычными настройками.
5. Discord Web в Chrome: выбрать тот же input, разрешить сайту микрофон, проверить речь.
6. Запустить QuickTime и Discord одновременно: оба читают одинаковый микрофон.
7. По отдельности отключить 3→1 и 4→2, сохранить. Подтвердить независимость каналов.
   Сохранение останавливает/перезапускает Swift IO; короткий разрыв при редактировании ожидаем.

## Надёжность

- Оставить поток на 30–60 минут; снять counters до/после. После startup счётчики Swift
  underrun/overrun и captureErrors должны оставаться постоянными. Driver missing frames
  могут расти без активного producer или при запуске клиентов; изучать совместно с записью.
- Сверить заполнение ring: ограниченное и без медленного ухода к нулю/ёмкости. PPM должен
  стабилизироваться; постоянные ±2000 ppm могут означать несоответствие часов/нагрузку.
- Закрыть главное окно: запись продолжается, MenuBarExtra открывает окно обратно.
- Отключить USB GoXLR: статус ожидания, приложение не падает, виртуальный input даёт тишину.
  Подключить тот же UID: захват восстанавливается, голос снова слышен.
- Sleep/wake: поток останавливается на сон и восстанавливается после появления устройства.
- Завершить приложение: микрофон даёт тишину, старый ring не повторяет звук.
- Запустить приложение снова: включённые маршруты восстанавливаются при разрешённой настройке.
- Включить автозапуск; выйти/войти в учётную запись и проверить разрешение Login Items.
- Переименовать/удалить устройство при закрытых клиентах; проверить системный список после
  уведомления HAL. При активном клиенте должно быть явное сообщение «драйвер занят».
- Удалить драйвер штатно, перезагрузить: устройства исчезают, чужие HAL bundles сохранены.

## Запись результатов

Зафиксировать OS/Xcode, подпись bundle, версии Discord/Chrome, физический UID, настройки
GoXLR Utility, число клиентов, buffer size, counters, продолжительность и факт прослушивания.
End-to-end latency измерять отдельным loopback/импульсным тестом; сумма буферов его не заменяет.
